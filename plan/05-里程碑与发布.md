**M1 的三处实测结论**（下一棒开工前必须知道）：

1. **两套编号在台账状态列会撞车**：布局门比的是**里程碑**号，而台账原写"模块 M1…M5"。
   里程碑 M1 翻 ✅ 后，`LAYOUT.LEDGER` 立刻报"台账行仍挂未完成"——**这不是假门**。

2. **1° 掩膜分辨不了 GCJ-02 位移**：位移约 250–600 m，1° 格约 111 km，跨不过格线。
   故 `water_track` 自带一张 0.0008°（≈89 m）的构造网格——§4.3 的 1° 是**上限**，更细合法。
   若要复现 D2，**必须**用这张细网格（`--mask data/fixtures/water_track/out/water_track_mask.json`）。
3. **海岸带纪律会吃掉语料的区分度**：与异类相邻的格算 `coastal`、不进分母。

| 判定守门 | `tests/test_decl.py` | 24 项：吃真实语料 `swapped_axis` / `declared_lie` 逐字段对拍金标 + 灰区 + 退出码契约 |
| 契约表清理 | `tests/test_unimplemented_contract.py` | `UNIMPLEMENTED` 删掉 `decl`（靶子过期 = 判据失效） |

**M2 的三处实测结论**（下一棒开工前必须知道）：

1. **§4.9 的 0 / 1 两行在裸命令下互斥，已定案**（`plan/00` 决策 ⑪）：`conflict` / `error`
   默认即命中 → `1`；且**灰区优先**——`undecidable` 一出现就是 `5`（除非 `--allow-undecidable`）。
   推论：`declared_lie`（0 个可判定样本）裸跑 → exit **5**，加 `--allow-undecidable` 才回落到
   `1`（它同时有 `conflict/magnitude`）。`swapped_axis` 无灰区 → exit `1`。
2. **`declared_lie` 的轴序项必须是 `undecidable` 而不是 `consistent`**：米域样本不进可判定子集
   （`|a|,|b| ≤ 180`），可判定样本数 `0 < 5` → `insufficient_samples`。这正是 `expect.json` 里
   `axis_decidable: false` 的含义，也是"两类样本互不串扰"的判据落点。
3. **`extent` 不许自己判轴序**：它按 `axis` 项的结论读分量（`lon_lat` / `lat_lon`），
   否则一份写反轴序的数据会同时被 `axis` 和 `extent` 判两次，DoD 的"单独命中"就失效了。

| 判定守门 | `tests/test_detect.py` | 23 项：D2 逐字段对拍金标 + 边界外不硬判 + 残差集合相等 + 两库分歧独立复算 + 退出码契约 |

**M3 的三处实测结论**（下一棒开工前必须知道）：

1. **默认 1° 掩膜复现不了 D2**：GCJ-02 位移 250–600 m ≪ 1° 格（≈111 km），三个假设全落同一格
   → 落水率相同 → 并列第一 → `undecidable`（`tests/test_detect.py::test_default_mask_rejects_gcj_offset_only_undecidable`）。
   **必须**用 `data/fixtures/water_track/out/water_track_mask.json`（0.0008°）。
2. **`distance_to_bbox_deg` 的框内语义是个坑**：改前对框内点返回 0，"距某库边界 < 0.05°"
   会把**所有框内点**判成边界带 → `boundary(h)=1` → 正确假设被扣 `0.25` 分、置信被压到 medium。
   修成"到矩形边的真距离"后 water_track 的 `boundary=0`、`confidence=high`，与金标一致。
3. **`declared(h)` 只作证据不替判定翻案**：声明 4326 时 GCJ02 / BD09 各扣 `0.30`，但 water_track 的
   落水率差（0.0 vs 1.0）足以让 GCJ02 仍以 `0.70` 胜出、置信 `high`（声明本身对不对，由分数与
   `confidence` 如实呈现）。

**M4 的三处实测结论**（下一棒开工前必须知道）：

1. **差分方向必须钉死**：三个实现覆盖的坐标系不同（`data/README.md` §1.5），若把不适用者一并
   塞进一次运行，会造出**虚假差分**（如 GCJ-02 目标下让 `proj4js_webmercator` 也参与）。
   定为：输入读作 `--target`，各实现转 WGS84，差分在 WGS84 输出之间做（`plan/00` 决策 ⑫）。
2. **金标对拍用输入坐标而非输出坐标**：`boundary_table` 用**输入**坐标直接代入两库边界框——
   与 `boundary_divergence/gen.py` 及 §1.3 对照表同口径。若改用 WGS84 输出坐标，就变成
   用被测物证明被测物（`plan/04` §二「参考实现三落点位」）。
3. **`not_converged` 是灰区不是冲突**：`(72.05, 0.83)`（gcoord 闭区间内、coordTransform_py 开区间外）
   迭代 100 次不收敛。归 `undecidable`（exit 5，`--allow-undecidable` → 0）——判不出来 ≠ 判定命中；
   同时**必须**出现在 `payload["not_converged"]` 里，**不得**静默返回"看起来对"的值
   （题面 §M3 纪律）。

**M5 的三处实测结论**（下一棒开工前必须知道）：

1. **R2 必须参与"级别计算"，不能只当文案**：`ring_order` 的默认 `warning` 由
   `R2_TOLERANCE_MARKER in RFC_R2` 推导（`_ring_order_status`）。测试把 `RFC_R2` 换成不含
   "SHOULD NOT reject" 的文本，断言级别升 `error`——删掉 R2 分支会立刻红。这是"假门"高发点：
   只断言"报告里有 ring_order"证明不了分级逻辑存在。
2. **结构性问题只能走 exit 4，不能靠 `error` 状态折算**：`error` 状态在 `errors.outcome_code`
   里是"命中 → 1"，而 §4.9 要求非法 JSON / 坐标对非数值 / 结构破碎一律 `4`。因此 `geojson.run()`
   先逐条收集 `structure/error`（`audit()` 可见），再整体抛 `InvalidInput`——失败路径零副作用，
   `report.json` / `report.md` 一个字节都不写。
3. **`axis_flip` 的"同一 bbox"必须可证**：只凭"同一 z/x 下出现 `y` 与 `2^z-1-y`"会误伤
   相邻两行的正常数据。判据定为：组级/单枚 bbox 相同，**或** `scheme` 明写 `xyz` / `tms`。
   fixture 的 `bbox` 只是"两枚指向同一 bbox"的声明（`[116,39,117,40]` 并非该瓦片的真实经纬足迹），
   本模块**不**用它反算瓦片号。

## 五、发布流程（M6 执行，现在只登记口径）

```
1. 交付面定稿（src/ + gen.py + pyproject）→ 重生成样例 → 全量测试
2. python -m build（在 git archive 导出的干净目录里 build）
3. 双装态验证（wheel + sdist 各装一次跑 --help 与一条真实命令）
4. SHA256SUMS → commit → tag（annotated）→ push main + push tag
5. gh release create <tag> <附件> --notes-file <正文>
6. 真下载回本地 → sha256sum -c + 逐字节 cmp
7. plan/RELEASE-M6.md：§一 tag 前事实 / §二 tag 后追加 / 覆盖对账表
```

### 发布门三档命令登记（`tools/check-release.py`，M6 落位）

| 档 | 命令 | 何时跑 | 判据面 |
|---|---|---|---|
| 离线（默认） | `py -3.12 tools/check-release.py` | 进 CI（布局门之后） | 交付面静态判据 + `dist/`/`SHA256SUMS` **条件复核**（0 份产物显式报出，不读 git、不联网） |
| tag 前 | `py -3.12 tools/check-release.py --pre-tag` | 打 tag 之前；tag 存在后必红 | 离线档判据 + "tag 尚未创建"前置事实 + `dist/`（wheel+sdist）与 `SHA256SUMS` **必须**齐备且可复核 |
| 在线 | `py -3.12 tools/check-release.py --online --tag <tag>` | Release 发布之后 | annotated tag 实存 + Release 附件下载 + `SHA256SUMS` 复核 + 附件解包树 × `git archive <tag>` 树**共有文件**逐字节相等（交集 ≥ 5，非 `diff -r` 零差异）+ tag 树 CLI 冒烟 |

退出码三档一致：0 全绿 / 1 有 FAIL / 2 用法错误。守门：`tests/test_release_gate.py`
（含"篡改一个附件字节 → 门必红"的变异与 --pre-tag 的"tag 前绿 / tag 后红"翻转）。

**三条时序纪律**：

1. **构建必须晚于交付面定稿**（sdist 里装着 README / LICENSE / pyproject 的快照）。
2. **不进 CI 的档**：`--pre-tag` 在 tag 推送时必红；`--online` 依赖网络与已发布事实。
   **CI 只跑离线档**。
3. **tag 树内不写字面值**（包 sha256 / tag 对象 OID / tag 指向的 commit）——写进树里就自指失效；
   字面值写进 tag 之后的 `plan/` 提交或 Release 正文。
